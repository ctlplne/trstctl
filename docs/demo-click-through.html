Discovery and NHI pitch

Preparation is outside the pitch clock

Earn the right to call it a live demo

Use a disposable, operator-owned lab. A Linux Compose stack does not supply a Windows IIS machine or an F5 appliance. Provision those separately. Record exact product, agent, operating-system, application, and device versions before rehearsal.

Prepared connector targets are not contacted targets. The shipped seed now creates clearly labelled Apache, IIS, and F5 destination records so the read-only pitch has concrete objects. It intentionally has zero enrolled agents, no target handshake, and no successful delivery receipt. A presenter must say “prepared, not contacted” until a candidate-specific live lab supplies the required host agent or network relay and independent listener proof.

Read-only tourInspect seeded or existing records. Explain screens. Do not claim a new deployment occurred.
Recorded evidenceShow a dated, candidate-labelled earlier rehearsal. State what ran and what was simulated.
Prepared live labExecute on the named target now. Compare before and after observations and retain the result.
  1. Pin the candidate. Complete the running-build check. The guide's SHA is an expectation, not a server measurement. A live stack at an older SHA is a different candidate.
  2. Establish trust and roles. Use the supplied public CA bundle and a scoped lab identity. Confirm the actual login and tenant with the operator; demo-admin@trstctl.local applies only to the shipped demo seed. No production credentials, browser certificate bypass, or disabled tenant isolation.
  3. Prepare real listeners. Start one Apache TLS site on a Linux host, or one IIS HTTPS binding on a Windows VM. Use lab DNS names, a trusted initial certificate, and a harmless response marker. Save the initial certificate fingerprint and expiry. Confirm the machine can tolerate a reload or brief binding interruption.
  4. Enroll the right agent. Host deployment needs a host-role agent on that machine; network scanning and appliance work need an eligible network-role relay. Enable only the needed job kinds in agent_channel.claimable_job_kinds. Set --relay-claim, the exact --host-exec-profile, and an encrypted --host-rollback-dir for host rollback. A heartbeat alone does not establish execution readiness.
  5. Constrain privileges. Enable the named native connector in operator configuration. Allow only the lab paths, executable/argument profiles, network ranges, ports, and credential references required. Keep secrets in protected files or secret handles, never the demo JSON, command history, screenshots, or this guide.
  6. Pick an issuer explicitly. For a keep-your-CA pitch, configure and rehearse that external CA and its validation prerequisites first. The generic endpoint-binding form does not expose issuer selection today. No silent switch to the built-in CA if the desired end-to-end path is unavailable: call that path blocked and show the exact gap.
  7. Rehearse two cycles. Prove initial delivery, a later replacement, endpoint verification, alert delivery to a controlled sink, and supported recovery. Repeat after an agent restart. Use fresh operation keys for new actions and the same key only for the same logical retry.
  8. Close the loop. Fill the rehearsal record. No current signed-in or external-target rehearsal is supplied by this guide. If any required step is missing, label the slot Read-only tour or Recorded evidence before presenting.

Use the CLI alongside the GUI—without revealing secrets

Install the documented trstctl-cli. Obtain a least-privilege lab token through the approved setup path; inject it through the protected process environment. Set TRSTCTL_SERVER, TRSTCTL_CA_FILE and the authenticated tenant context. The commands below read metadata; they do not configure or deploy a target.

For mutations, use the command-specific --help and the pinned API schema. Keep one stable idempotency key per logical action across retries. Do not use a fresh key simply because an issuance response timed out; first reconcile whether the CA already issued it.

Appliance CLM · network operations

F5: show the certificate on the traffic path

Keep your issuing CA and your load balancer. Use one controlled lifecycle to install the replacement, bind the intended profile, and check what the application presents.

Lab: one operator-owned BIG-IP with recorded firmware, partition, Client SSL profile, virtual service and SNI name; a reachable network-role relay; protected management credentials; a rehearsed issuer path; and a current, valid predecessor. Presenter truth contract

A receipt is not a TLS handshake

1 · source fingerprintThe certificate originally observed on the exact host, port and SNI name.
2 · expected fingerprintThe approved replacement returned by the selected issuer and assigned to that target.
3 · observed fingerprintThe certificate that a new connection actually receives after deployment.

A live success requires the expected and observed fingerprints to match, the hostname/chain to validate, and the application to answer. Record timestamp and verification vantage. Renewal also needs a replacement cycle and the next scheduled action. A successful connector command alone proves less.

“Can we keep our CA?”

Yes, that is the product direction and there are external issuer adapters. State the exact issuer and operations proved for this candidate. Some adapters do not implement revoke or fully unattended validation. The current GUI does not yet unify every external-CA lifecycle handoff.

“Does it support our IIS / Apache / F5 version?”

“Here is the exact version and topology we rehearsed, and these are the operations that passed.” Without that record, say implemented and awaiting qualification—not fully supported. No live vendor qualification was performed when writing this guide.

“What if the agent or CA disappears halfway through?”

Show the durable operation, whether submission happened, retry policy and last known target state. If the CA result is indeterminate, reconcile before retrying. Do not claim exactly-once behavior from a provider that cannot support reconciliation.

“Can we use it without the GUI?”

Yes: the REST API, JSON CLI and SDKs expose substantial capability. Explain which commands queue work, how the client polls for the terminal outcome, and what evidence proves success. Standard MCP-client compatibility and generic end-to-end workflow resume must be demonstrated separately.

“Does every NHI source discover data automatically?”

No. There are real network, host and cloud collectors, plus metadata ingestion surfaces. Show source kind, credentials/scope, last collection and provenance. An uploaded observation is not a live vendor connector.

Demo failure protocol: identify the failed stage in one sentence, preserve its evidence, stop new mutations, and offer a labelled recording or a narrower read-only tour. Agree a follow-up test; do not debug with production secrets during the sales call.

trstctl manages credentials used by machines, not people. A machine might be a web service, build bot, Kubernetes workload, router, database, or AI agent. trstctl finds its credentials, applies policy, records every state change, and delivers replacements.

OwnerThe person or team accountable for the machine.
Machine identityThe service, workload, device, bot, or agent.
CredentialThe certificate, key, secret, or token that proves identity.
Deployment targetThe system where that credential must work.
DiscoverFind certificates, secrets, tokens, SSH keys, and workloads.
DecideApply tenant policy, ownership, risk, and approval rules.
IssueAsk an isolated signer or external CA for a credential.
DeliverUse a connector to place it where the machine needs it.
ProveKeep immutable events, receipts, audit exports, and evidence packs.
Rotate or revokeReplace healthy credentials on schedule and remove unsafe ones quickly.

The 10-minute proof loop

Use this short, read-only path to answer the first customer question: “Can I see one machine credential move from discovery to action and evidence?”

  1. Sign in and confirm that your tenant and role are visible.
  2. Open the dashboard and identify what needs attention first.
  3. Inspect discovery to see where a credential came from.
  4. Open a certificate to connect owner, machine identity, credential, and deployment target.
  5. Open an incident to see the safe remediation plan and evidence.

If you can explain those five screens in plain language, stop there. Continue with the full walkthrough only when you want protocol, governance, graph, connector, and administration detail.

Demo numbers can move

Plain-language glossary

The shortest useful definition of the terms used in the UI.

NHI
Non-human identity: a service, workload, bot, device, agent, or other machine actor.
Credential
Proof a machine uses to authenticate, such as a certificate, secret, API key, token, SSH certificate, or SVID.
Identity
The durable machine record. It can hold different credentials over time as they rotate.
X.509 certificate
A signed digital identity document used mainly for TLS and device/workload authentication.
CA
Certificate authority: the system trusted to sign certificates.
Profile
Rules limiting what a CA may issue: lifetime, names, algorithms, purposes, and protocol.
Tenant
An isolated customer or organizational boundary. Every stored row and query is tenant-scoped.
RLS
PostgreSQL row-level security: the database itself prevents one tenant from reading another tenant’s rows.
Event
An immutable statement that something happened. Events are the source of truth for lifecycle state.
Projection
A query-friendly table built from events, such as the certificate inventory or audit view.
Outbox
A durable queue record written with the state change before an external call is attempted.
Connector
A runtime implementation that deploys, tests, rolls back, or right-sizes a credential at a target system.
Signer
The isolated process that performs private-key operations. It is separate from the web control plane.
Rotation
Issue a replacement credential, deploy it, verify it, and retire/revoke the predecessor.
Blast radius
The identities and resources affected if a credential is stolen, revoked, or unavailable.
CBOM
Cryptographic bill of materials: an inventory of algorithms, key sizes, TLS versions, and crypto dependencies.
SPIFFE / SVID
A workload-identity standard and its short-lived identity document.
FIPS
A regulated cryptographic-module posture. A license flag alone does not turn a normal binary into a FIPS-built artifact.

Troubleshooting

Simple recovery steps for the local demo.

The page says “token exchange failed”

Close the error tab, reopen the demo root, and click Continue with SSO again. If it repeats, the local OIDC sidecar needs to be reattached; ask the demo operator to restart it.

The browser cannot connect

Confirm the address shown in Walkthrough target. Copy /public-trust/control-plane.crt from the trstctl service, inspect its SHA-256 fingerprint, and import that certificate-only file into the browser trust store. Do not bypass the warning or replace HTTPS with a plaintext proxy. See Trust local evaluation TLS. The demo stack must remain running on this machine.

A screen has no rows

Read the empty-state explanation. Some integrations need a real external target or scan input. “No rows” is different from “not implemented”; the page should say what configuration or action is missing.

A connector receipt says failed

That is expected when the demo has no real vendor endpoint or credentials. The useful part is the durable attempt, error, retry/circuit-breaker state, and evidence receipt.

The FIPS row says licensed but inactive

Correct. The demo uses the standard image. Actual approved-mode testing requires the artifact produced by make fips-build plus the deployment-specific validation and operator artifacts listed on the Platform page.
